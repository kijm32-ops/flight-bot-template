# Role Policy

이 정책은 작업을 `CHAT`, `WORK`, `CODEX` 중 어디에서 수행할지 결정한다.
역할은 편의상의 라벨이 아니라 실행 경계다.

## 1. Routing order

다음 순서로 판단한다.

1. 사용자가 `CHAT / WORK / CODEX`를 명시했고 현재 환경의 도구로 안전하게 완료할 수 있으면 그 역할을 우선한다.
2. 현재 Chat 도구로 품질 손실 없이 완결할 수 있으면 난도·답변 길이·도구 사용량과 무관하게 `CHAT`에 남는다. 조사·비교·설계·코드 검토·간단한 파일/저장소 변경과 검증은 가능한 범위에서 Chat이 직접 수행한다.
3. 로컬 저장소 전체 탐색, 터미널 명령, 테스트/build/migration처럼 Codex 고유 실행환경이 작업의 핵심이면 `CODEX`.
4. 다단계 브라우저/컴퓨터 조작, 외부 앱을 넘나드는 실행, 저장소 밖 여러 파일의 직접 제작·수정과 검증, 반복 수작업 위임처럼 현재 Chat에 없는 실행 환경이 실제로 필요하면 `WORK`.

애매하면 "현재 Chat 도구로 품질 손실 없이 끝까지 완료할 수 있는가"를 먼저 본다. 어려운 추론, 긴 조사, 웹 검색 몇 번, 간단한 표·문서 제작은 그 자체로 전환 사유가 아니다. 필수 실행 능력이 부족할 때만 handoff 한다.

## 2. CHAT

> Claude 계열에서는 Chat, Cowork, Code가 하나의 사용 한도를 공유한다. 이 경우 아래 completion-first 원칙은 적용하지 않고 `.ai/MODEL_POLICY.md`의 "Claude catalog"와 사용량 절약 규칙을 따른다. 필요한 사고와 검증을 생략하라는 뜻이 아니라, 모델·도구·대화 길이를 필요한 만큼만 쓰라는 뜻이다.

기본 목표는 **completion-first autonomous execution**이다(OpenAI 계열). 비용 절감을 위해 필요한 작업을 생략하거나, 되돌릴 수 있는 중간 단계마다 사용자 확인을 요구하지 않는다.

허용:

- 요구사항 정리, 설계와 아키텍처 판단
- 코드 리뷰, 장애 원인 분석, 실패 케이스 검토
- 구현 범위와 검증 기준 작성
- 현재 제공된 도구를 사용한 파일/저장소 읽기와 수정
- 요청 범위 안의 되돌릴 수 있는 소스/문서/설정 변경
- Git commit과 비강제 fast-forward push. 단, push 자체가 운영 배포·외부 발송 등 HIGH 작업을 유발하는 것으로 확인되면 Safety 승인 게이트를 따른다.
- 현재 환경에서 가능한 정적 검증과 원격 상태 확인
- 필요한 경우 Work/Codex용 정확한 handoff 작성

진행 원칙:

- `SUCCESS / BLOCKED / NEEDS_USER` 중 하나가 될 때까지 가능한 작업을 계속한다.
- 다음 행동이 사용자 선택에 따라 실제로 달라지지 않으면 확인을 요청하지 않는다.
- 여러 가설이 성립하면 가장 가능성이 높은 가설에 대해 **다음 행동을 결정하는 최소 검증**만 수행한다. 기각되면 중간 승인을 기다리지 않고 다음 가설로 이동한다.
- 가설 하나의 실패나 중간 검증 결과를 보고하기 위해 작업을 멈추지 않는다.
- 되돌릴 수 있는 변경은 작은 단위로 실행하고 결과를 관찰한다. 결과가 나쁘면 되돌리거나 다음 가설로 이동한다.

제한:

- 실행하지 않은 명령이나 테스트를 실행했다고 보고하지 않는다.
- 실제 저장소를 수정하지 않은 상태에서 구현 완료라고 선언하지 않는다.
- 현재 Chat 도구에 필수 실행 능력이 없거나 Safety 승인/사용자만의 결정이 필요한 경우에만 해당 지점에서 handoff 또는 사용자 입력을 요구한다.

## 3. CODEX

Claude Code도 로컬 저장소 탐색, 파일 수정, 명령 실행이 핵심인 환경이므로 `CODEX`로 취급한다. 별도 역할을 만들지 않는다.

허용:

- 저장소 탐색과 실제 파일 읽기
- 코드/설정 수정
- 파일 생성/삭제
- 명령 실행
- 테스트, typecheck, lint, build
- migration 생성 및 비파괴적 검증
- 실제 실행 결과 확인

제한:

- 확정된 아키텍처를 임의로 바꾸지 않는다.
- 요청 범위를 넘는 대규모 리팩터링을 섞지 않는다.
- 구현 중 설계 변경이 필요해지면 최소 안전 경계에서 중단하고 아래 형식으로 기록한다.

```text
BLOCKED_BY_DESIGN
- discovered issue:
- affected files:
- why current design cannot continue safely:
- recommended decision:
```

## 4. WORK

허용:

- 여러 정보원과 파일을 실제로 오가며 처리하는 업무
- 웹 조사와 앱/파일 작업을 포함한 다단계 업무
- 현재 Chat 도구로 완결할 수 없는 다단계 문서, 스프레드시트, 프레젠테이션, 보고서 제작
- 복합 업무의 일부로 필요한 제한적 코드 작업

제한:

- 저장소 구현 자체가 주목적이면 `CODEX`로 라우팅한다.
- 난도, 답변 길이, 장시간 작업, 도구 사용, 완성 산출물이라는 이유만으로 `WORK`를 선택하지 않는다.
- 코드 변경이 커지거나 저장소 검증이 핵심이 되면 `CODEX`로 전환한다.

## 5. Mandatory role declaration

프로젝트 작업을 시작할 때 `SESSION_STATE.md`의 `ROLE`을 먼저 확정한다.

실제 파일 변경 또는 명령 실행 전에는 다음 조건을 만족해야 한다.

- `ROLE`이 `CHAT`, `WORK`, `CODEX` 중 하나다.
- 현재 작업이 해당 역할의 허용 범위와 일치한다.
- `MODEL_POLICY.md`에 따른 실행 프로필이 기록되어 있다.
- 역할이 맞지 않으면 실행하지 않고 올바른 환경으로 handoff 한다.

중앙 Harness CLI를 사용할 수 있다면 실행 전에 `gate`로 역할을 검사한다.

## 6. Handoff rule

역할 전환 시 이미 확인한 사실을 다시 조사하지 않도록 다음을 남긴다.

- 현재 목표
- 확인한 파일/근거
- 결정된 설계
- 변경 금지 범위
- 다음 역할이 수행할 정확한 작업
- 검증 기준
- 알려진 위험

역할 전환은 작업 실패가 아니라 책임 경계의 변경이다.
